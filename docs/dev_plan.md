## 0. 순서 결정 원리

개발 순서는 "쉬운 것부터"가 아니라 **"가장 위험한 가설부터"** 입니다. 이 게임에는 틀리면 프로젝트가 무너지는 가설이 세 개 있고, 각 단계는 이 가설을 하나씩 검증하는 실험이어야 합니다:

- **가설 A**: "배를 그리는 것 자체가 재미있다" (틀리면 게임 전체가 무의미)
- **가설 B**: "위치 배치에서 조향이 창발한다" (틀리면 아이템 시스템 재설계)
- **가설 C**: "규칙표에서 의도하지 않은 해법이 나온다" (틀리면 그냥 평범한 퍼즐 게임)

그래서 각 날의 끝에는 **통과 질문**을 붙입니다. 통과 못 하면 다음 날로 못 갑니다. 일정이 5일뿐이므로 통과 질문 옆에 **폴백**(무엇을 잘라서 살아남을 것인가)을 같이 명시합니다 — 압축 일정에서는 "실패했을 때 무엇을 포기할지"를 미리 정해두지 않으면 그 자리에서 멈춥니다.

### D1 — 8/6 · 코어 필: 그리기와 항해 **[가설 A]**

원본 1단계. 만드는 것: 선체 그리기 캔버스 + 실시간 오버레이(무게중심 G·저항 타원·흘수 게이지) / 형상 → 3대 파라미터 자동 산출 / 기본 3종 장치(키·노·닻) / 카메라(위치 추적 + 줌, **회전 금지**) / 헤딩 인디케이터 + 예측 궤적선.

궤적선을 D1에 넣는 이유는 심적 회전 문제를 여기서 실측해야 하기 때문입니다. on/off 토글을 만들어 비교합니다.

**통과 질문 (가설 A)**: 아무 목표 없이 빈 바다에서, 다르게 그린 배 세 척(길쭉/둥근/비대칭)의 조작감이 명확히 다르게 느껴지는가? 뾰족한 배와 둥근 배를 몰아본 사람이 그 차이를 **말로 설명할 수 있는가?**

**폴백**: 차이가 안 느껴지면 멈추고 형상-물리 매핑의 **과장 계수**를 올린다. 시뮬레이션의 사실성보다 차이의 체감이 우선.

### D2 — 8/7 · 창발 조향 + 규칙 엔진 **[가설 B·C]**

원본 2·3단계 병합. 두 단계 모두 "코드가 아닌 데이터에서 행동이 나오는가"를 묻고, 돛(바람 × 천)이 양쪽 검증을 동시에 만족시키기 때문에 병합이 성립합니다.

만드는 것: 아이템 부착 시스템(위치·방향·질량 통일 모델) + 부스터·닻·밸러스트·돛 / 토크 자동 계산 / 트리거 키 바인딩 UI + 설계 화면 키 오버레이 / 바람 벡터장 + 온도 스칼라장 / 재질 3종 / 상태 전파(불붙음·젖음) / **JSON 규칙표 로더**.

규칙표를 코드가 아닌 데이터로 만드는 것이 이 날의 최우선 산출물입니다. 이후 모든 밸런싱과 맵 제작이 이 파이프라인 위에서 이뤄지므로, 여기서 아키텍처가 굳습니다.

**통과 질문 (가설 B)**: 조향 코드를 한 줄도 안 짰는데, 좌우 부스터 배치만으로 슬라럼을 통과하는가? 닻 드리프트가 성립하는가?

**통과 질문 (가설 C)**: 화염 지대 테스트 맵에서, 의도 해법(철배) 외에 **"물웅덩이를 먼저 지나 젖은 나무배로 통과"** 같은 비의도 해법이 규칙 조합만으로 실제 성립하는가? 성립 안 하면 규칙표의 상성 정의를 수정한다 — **맵에 예외 코드를 넣는 순간 원칙 1 위반이므로 금지.**

**폴백**: 시간이 부족하면 돛을 자르고 부스터로 가설 B만 검증. 규칙표는 불/젖음 2줄만 남겨도 가설 C는 성립한다.

**결과 (2026-08-07)**: 폴백 없이 완료. `npm run bench` 71/71 통과.

- 오전에 **키 조향을 폐기하고 좌우 노 스트로크로 교체**했다(계획 외 추가). 키만 전용 양력식을 갖고 있어 "조향 코드 0줄"의 유일한 예외였는데, 노를 좌우로 나누면 조향이 `τ = −y·F` 하나로 환원된다. 키는 카탈로그의 부착 아이템으로 내렸다 — 5 m/s 에서 노 조향 0.00° vs 키 53.27° 라는 트레이드오프가 그 자리를 정당화한다.
- **가설 B**: 같은 부스터를 (x, y, angle) 만 달리해 얹으면 직진 0.00° / 편측 6초 112° / 미러 부호 반전 / 양현 동시 상쇄 / 측면 90° 게걸음이 전부 나온다. 좌↔우 1.6초 교대는 방향 전환 7회·진폭 4.6°·누적 1.9° 로 나선이 아닌 지그재그. 현측 닻은 3초에 28.1° 피벗(닻점 이동 0.0 mm). **슬라럼 실통과만 사람 판정으로 남는다.**
- **가설 C**: 같은 존·같은 규칙·같은 코드에서 **출발점 하나만** 다른 두 항해로 판정했다. 물웅덩이(x=15) 경유 배는 45초 생존(x=121)하고 발화 이벤트가 아예 없다. 웅덩이를 건너뛴 배는 x=43 에서 연소 파괴. 젓지 않고 표류하면 젖음이 말라 결국 타므로 비의도 해법에도 대가가 있다.
- 규칙표는 10줄, 필드 정의는 6존. 스키마 밖 규칙(모르는 조건·효과·필드)은 **로드 시점에 throw** 하고, 규칙표에 map·zone·script 를 가리키는 필드가 없다는 것도 벤치가 검사한다 — 원칙 1이 규약이 아니라 구조적으로 불가능하다.
- D3 로 넘기는 전제: 아이템 인스턴스 ID 기반 트리거(§7.5 무효화), `kind:'impulse'` 자리 예약(대포 반동), `hull.status` 조각 승계(불붙은 배를 쪼개도 계속 탄다), 필드 스키마의 해류·전기·자기 자리. **역풍 돛 페널티는 현재 거리 38%** — 2장이 "돛을 떼라"를 강제하려면 이 값을 키워야 한다.

### D3 — 8/8 · 파손 지오메트리 + 3맵 + 게임 루프

원본 4·5단계 압축. 만드는 것: 충격 이벤트 → 폴리곤 차감 → 파라미터 재계산 파이프라인 / 절단 판정 → 다중 강체 분리 / 아이템 탈락·트리거 무효화 / 대포·암초 / 맵 JSON 포맷 + 3맵 / 설계→출항→실패→재설계 UI 완결 / 실패 분석 화면(항적 고스트 + 침몰 사유 배지).

**3맵 편성** — "규칙 학습 → 같은 규칙의 반전 → 재질 전환"이라는 커리큘럼 뼈대의 최소 단위:

| 장 | 맵 | 학습 목표 | 핵심 규칙 |
|---|---|---|---|
| 1 | 순풍 해협 | 그리기, 흘수, 큰 돛 | 천 + 바람 = 추력 |
| 2 | 역풍 협곡 | 돛 축소/제거, 노·부스터 도입 | 1장의 정답이 페널티로 반전 |
| 3 | 화염 화산대 | 철 재질, 무게-흘수 재설계 + **포탑·암초로 파손·절단 집중** | 나무 + 불 = 파괴 / 절단 = 분리 |

원본의 7장(빙해 여울, 다단 분리)을 3장으로 끌어올려 §7.3의 하이라이트를 살립니다.

**통과 질문**: HP바 없이 **거동 변화만으로** 자기 배의 피해 상태를 인지하는가? 3맵 전부 클리어 가능한가? **맵별 특수 코드가 실제로 0줄인가?**

**클리어의 주체는 주인공이다** (`src/game/crew.js` · `src/game/goal.js`). 배가 아니라 갑판 위의 사람이 도착 지점에 들어와야 클리어입니다 — 폴리곤 겹침으로 재면 뱃머리만 밀어 넣어도, 잘려 나간 파편이 표류해 들어가도 클리어가 되어 §7이 배를 쪼갤 수 있게 만든 전제가 무너집니다. 주인공은 설계 화면 한가운데에 서 있고, 그를 감싸도록 그려야 출항할 수 있으며, 절단되면 §7.5 소속 폴리곤 판정으로 자기가 서 있던 조각을 타고 갑니다.

**폴백**: 3장이 안 끝나면 2장까지만 + 3장을 "샌드박스(자유 항해 + 포탑)"로 격하. **파손 데모는 반드시 남긴다** — §7이 이 게임의 차별점이므로 영상의 핵심 컷.
